# pgrx 0.20.0 upgrade and benchmarks

Date: 2026-11-13. Baseline: commit `434b8fb`, pgrx 0.19.3. Candidate:
`codex/pgrx-020-upgrade`; source hashes and raw results are in the
[evidence directory](pgrx-0.20.0-2026-11-13/).

## Changes

Reviewed the upstream [release notes](https://github.com/pgcentralfoundation/pgrx/releases/tag/v0.20.0)
and linked migration guide. Pinned the pgrx family and CLI to 0.20.0 and Rust
to 1.99.1. Support is now PG15-19, following upstream's removal of PG14.
Replaced the removed varlena setter with generated `SET_VARSIZE!`. Builds use
matching Clang/libclang/LLVM tools and patched PostgreSQL headers containing
the upstream composite-datum security fix.

The baseline `ST_EvilTransform(42, 990001)` terminated the PG18 backend with
SIGSEGV. The candidate verifies the actual PostGIS geometry type, including
domains, before interpreting the Datum as a pointer. PostGIS object lookup now
uses its owning schema independently of the caller's search path.

Performance changes remove an intermediate geometry malloc/memcpy/free by
transferring the librttopo buffer directly, borrow Jenks aggregate state during
finalization instead of cloning its count map, and stream array conversions
without an intermediate vector. The C context explicitly uses malloc/free.

The existing release settings remain opt-level=3, fat LTO, one codegen unit,
and C -O3. No CPU-native target, fast-math, instrumentation flags, or
`unsafe-postgres` feature was enabled. Installation privilege settings were
not changed, and no SQL-only installer is included.

## Method

- Local Docker Linux aarch64 VM, 8 CPUs / approximately 15.6 GiB RAM,
  Apple M4 Pro host. These are ARM64 measurements, not x86_64 results.
- PostgreSQL 18.7 and 19rc2, PGDG Debian Trixie packages; PostGIS 3.7.0,
  GEOS 3.15.0 and PROJ 9.9.0 on both servers.
- Rust 1.99.1 and Clang/libclang/LLVM 19.1.7. Both builds use the same Rust,
  server headers, native libraries and release optimization profile.
- Coordinates: 200,000 points, setseed(0.42), existing query shapes. The composed
  query includes 4326 -> BD09 setup as well as BD09 -> 3857. Expressions can be
  evaluated for both ST_X and ST_Y; these are whole-query timings.
- Jenks: 100,000 rows, 1,000 distinct values, 7 classes, work_mem=8MB.
- JIT and parallel query workers disabled. Builds and tests finished before
  timing. One complete warm-up (run 0) excluded, then five serial samples
  per workload, build and PostgreSQL version. Values below are median
  EXPLAIN ANALYZE Execution Time, milliseconds.
- This compares the upgrade plus implementation changes together and does
  not isolate the contribution of each change.

## Results

| Workload | PG18 baseline | PG18 candidate | PG19 baseline | PG19 candidate |
| --- | ---: | ---: | ---: | ---: |
| Native 4326 -> GCJ02 | 122.945 | 120.606 | 126.215 | 117.467 |
| Regex SQL 4326 -> GCJ02 | 5466.402 | 5546.002 | 5576.511 | 5457.143 |
| Native 4326 -> BD09 -> 3857 | 337.275 | 320.751 | 334.725 | 321.285 |
| Regex SQL 4326 -> BD09 -> 3857 | 15705.911 | 15343.097 | 15350.916 | 14996.976 |
| CartoDB SQL Jenks | 92.297 | 84.067 | 88.080 | 82.898 |
| Rust Jenks array | 10.746 | 10.493 | 9.837 | 9.254 |
| Rust Jenks aggregate | 8.998 | 9.114 | 8.261 | 8.357 |

Native direct medians decreased 1.9% on PG18 and 6.9% on PG19, with overlapping
sample ranges. Composed medians decreased 4.9% and 4.0%, with non-overlapping
ranges in these samples. Unchanged SQL controls also moved, so these figures
are indicative rather than statistical proof of a fixed improvement. Jenks
array ranges overlap and aggregate medians increased about 1.3% / 1.2%; no
clear Jenks timing win is claimed. The copying reductions still remove
avoidable allocations. Full min/max ranges are in `summary.txt`.

The native and regex implementations already use different Earth-radius
constants; SQL timings are reference costs, not evidence of identical numeric
semantics. Within each server, native output hashes for both coordinate
workloads, Jenks results and ZM/line/polygon/empty-collection fixtures match the
baseline byte for byte. See each pair of `results.txt` files.

The evidence includes plans, samples, a reproduction driver and median parser.
The driver expects this checkout at `/work`, installed extension binaries,
and disposable servers on Unix socket `/tmp`, ports 5418/5419. Run
`bash run-benchmarks.sh baseline 18` and the other build/version combinations.
`python3 summarize.py` reads `/tmp/bench-results`. Run 0 is excluded.
These scripts recreate benchmark tables; use disposable databases only.

## Validation

- Core Rust tests: 13 passed. Release-profile suites: 28 passed on each of
  PG18.7 and PG19rc2, including 15 database tests and the 13 core tests.
- Release compilation checks: PG15.20, PG16.16, PG17.12. Release builds:
  PG18.7 and PG19rc2.
- A pre-existing WKT-text assertion also failed with the old binary. Its
  reference uses a different Earth radius. It now checks SRID and numeric
  coordinates at the core reference tests' 1e-6 tolerance; formulas are unchanged.
- Scalar misuse returns an SQL error; geometry domains preserve type and
  coordinates. Fresh backends with search_path=pg_catalog successfully call
  the schema-qualified native API on both servers.
- ARM64 DEB packaging passed for PG18 and PG19 with package_debs.sh.
- Rust formatting, shell syntax and diff whitespace checks passed.
- CI is configured for amd64/arm64 and PG15-19 SQL tests. Remote CI, a full Dockerfile
  rebuild, RPM packaging and PG15-17 runtime suites were not executed locally.
  No release or deployment was performed.

## Further opportunities

1. Avoid full detoasting for an SRID read and reuse the detoasted input for
   transformation. Include large toasted geometries in the benchmark first.
2. Replace per-row OidFunctionCall2Coll setup with a memory-context-owned
   FmgrInfo cache, accounting for catalog invalidation and PostGIS recreation.
3. Use borrowed pgrx arrays to avoid the initial Vec conversion as well as
   the intermediate vector already removed; preserve NULL/numeric semantics.
4. Measure high-cardinality Jenks separately: this duplicate-heavy workload
   does not characterize the dynamic-programming path's worst cost.

These are follow-ups, not changes whose gains were measured here.
